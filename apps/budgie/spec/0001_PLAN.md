# Budgie initial setup plan

Status: ready for implementation. This document plans the work; it does not provision services or implement the app.

## Scope and decisions

- Build a browser-only budgeting app named Budgie using Vite and the internal frappe package (`@charismaticalli/frappe`).
- Use `apps/budgie/` as the app directory, matching the explicitly requested spec location; package name is `@charismaticalli/budgie`.
- Exactly three runtime dependencies: `effect: catalog:`, `@charismaticalli/frappe: workspace:*`, and a pinned `@supabase/supabase-js` version. No UI package or additional router/query library.
- Use Vite, TypeScript, and Vitest as development dependencies, plus the existing repository formatter/linter tooling needed by its required checks. Reuse catalog versions. Keep Supabase CLI installation a documented development prerequisite.
- Local Supabase provides real authentication. Support email/password login and signup, email OTP, GitHub OAuth, password recovery, session restoration, and logout.
- Primary routes are `/login` and `/accounts`. Accounts is the initial dashboard.
- Account persistence belongs in Supabase eventually. For this milestone, render an account-name form whose submission does nothing: prevent browser navigation, create no record, and show no fabricated success. Include a short “Account creation is coming soon” hint. No account table, migration, CRUD service, or fake stored accounts in this milestone.
- Style a responsive purple/blue interface with light, dark, and system theme preferences.

## Repository foundations

Use `apps/site` as reference for Vite configuration, bootstrap/mount lifetime, frappe routing, auth resources, and theme behavior. Implement app-owned modules rather than importing source from the site app. Preserve existing site behavior and root default dev/build targets; add explicit Budgie commands.

Relevant references:

- `apps/site/src/bootstrap.ts`: scoped mounting, resource layers, browser history, query configuration.
- `apps/site/src/auth.ts`: resource service and replaying session stream; its adapter is a mock, not real authentication.
- `apps/site/src/examples/routing/`: typed destinations, transitions, views, and navigation tests.
- `packages/frappe/src/query/runtime.ts`: one application-owned query configuration; partition changes retire the old store.
- `apps/site/src/features/theme/` and `apps/site/src/style.css`: persisted theme selection, system preference updates, and CSS structure.
- `.agents/skills/css/SKILL.md` and `.agents/skills/effect/SKILL.md`: implementation conventions.

Use `Option` for optional values, exhaustive `Match` for branching, top-level imports, named options for related arguments, Effect schemas at external boundaries, typed errors, and scoped service lifetimes. Inspect pinned/vendored Effect APIs before implementation.

## 2. Local Supabase development

Check the installed CLI version and command help before using commands or configuration fields. Initialize an app-owned Supabase project under `apps/budgie/supabase/`; run its CLI commands from `apps/budgie`. Use a Docker-compatible container runtime and document installation/startup prerequisites and any port conflicts. Follow the [local development guide](https://supabase.com/docs/guides/local-development).

Configure the app origin, allowed auth redirects, email signup/confirmation, and local email capture. Explicitly enable email confirmation so local testing exercises the intended signup lifecycle. Configure the OTP email template to deliver a code rather than the default magic link, and verify its length against the selected configuration. See [email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless).

Provide a tracked `.env.example` with browser-safe Supabase URL and publishable-key placeholders. Local CLI installations that expose the legacy anon key may use that public equivalent. Keep actual local environment files ignored. Feed Vite environment values into Effect configuration at the application boundary; report missing configuration as a useful startup error.

Configure GitHub credentials through Supabase server-side environment references, never Vite variables. Register a development GitHub OAuth application with the local Supabase Auth callback URL reported by the local configuration; this is distinct from the frontend `/auth/callback` URL. Document both URLs and setup steps from the [GitHub provider guide](https://supabase.com/docs/guides/auth/social-login/auth-github). GitHub login requires external connectivity and developer-owned OAuth credentials even though Supabase runs locally. Missing credentials must leave a clear unavailable-provider state and must not prevent email development.

Document initialization, start, status, stop, app startup, and how to open the local email inbox. Do not create a hosted project or deploy anything. Database schema design is deferred with account persistence; when it is added, load the Postgres skill and implement ownership/RLS tests rather than relying on client query partitioning for authorization.

## 3. Auth adapter and session lifecycle

Create one Supabase client per app runtime and expose it through an Effect resource layer. Let the SDK own persisted sessions, refresh, and cross-tab auth synchronization. Adapt SDK promises into named effects with typed auth errors; components depend on the app auth service rather than calling the SDK.

Expose operations for password login, signup, OTP request/verification, GitHub login, password-reset request/update, and logout. Expose a replaying `Stream<Option<User>>`, with a stable Supabase user ID and optional email. Also model initialization and recovery state explicitly: `None` alone cannot distinguish startup from confirmed logout or represent password recovery.

Subscribe once to SDK auth events, keep callbacks synchronous and lightweight, and process subsequent work through the scoped Effect runtime. Ensure initial session discovery cannot overwrite a newer event. Unsubscribe and stop app-owned consumers during disposal. The [auth event API](https://supabase.com/docs/reference/javascript/auth-onauthstatechange) is the integration boundary.

Treat initialization failure separately from signed-out state, with retry UI. Distinguish invalid credentials, invalid/expired codes, rate limiting, and transport failures where useful. Pending forms prevent duplicate submissions. Do not optimistically clear the session after a failed logout; real signed-out events remain authoritative.

## 4. Routes and authentication flows

Use frappe typed routes and browser history, with deterministic auth-aware transitions:

| Route             | Behavior                                                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `/`               | Wait for auth initialization, then replace with `/login` or `/accounts`.                                                              |
| `/login`          | Password login, signup, email OTP, GitHub login, and recovery-request modes. Ordinary authenticated sessions redirect to `/accounts`. |
| `/accounts`       | Protected dashboard; signed-out users redirect to `/login`.                                                                           |
| `/auth/callback`  | Complete OAuth/signup callback processing before ordinary route guards run.                                                           |
| `/reset-password` | Complete recovery callback and allow the authenticated recovery session to set a password.                                            |
| Unknown route     | Accessible not-found view with a link to the appropriate home destination.                                                            |

Use replacement navigation for automatic redirects, preserve browser back/forward behavior, and render a neutral loading view while auth initializes. Do not mount protected content before authentication is resolved.

Use PKCE for redirect-based flows. Assign callback exchange to exactly one owner, configure SDK URL processing accordingly, and remove consumed auth parameters from browser history. Show actionable callback errors for missing, expired, already-used, or rejected callbacks. Document that PKCE links require the initiating browser's verifier; see [PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

Password signup displays a confirmation-pending state when no session is returned. Provide confirmation resend. For OTP, use explicit sign-in versus signup intent: ordinary sign-in must not silently create a user, while signup may do so. Include code entry, resend, pending, and expired-code states.

Recovery requests always show a neutral email-sent message. Recovery state takes precedence over ordinary authenticated redirects; the user must be able to submit and confirm a new password before continuing to `/accounts`. Reloading the recovery page with a valid recovery session must remain usable. Follow the [password auth/recovery guide](https://supabase.com/docs/guides/auth/passwords).

## 5. User-partitioned query client

Call `Query.configure` once during bootstrap, using an application-owned `Signal<Option<UserId>>`. Populate it from the auth user stream:

- Initializing, signed out, or unable to establish identity: `None`.
- Authenticated: `Some(user.id)`.
- Token refresh or metadata updates for the same ID: preserve the partition.
- Logout or a different user ID: retire cached data and in-flight query work through frappe's existing partition behavior.

Coordinate partition updates and auth routing so protected observers cannot render old-user data during transitions. Dispose auth consumers and queries with the application scope. Do not implement a parallel cache or key partitions by token/email. Use controlled query fixtures to test integration now; no invented production accounts endpoint is needed for the placeholder form.

## 6. UI and themes

Build semantic, labeled auth forms and a minimal accounts shell with heading, empty state, account-name form, logout, and theme selector. Support keyboard navigation, visible focus, inline errors, status announcements, appropriate autocomplete attributes, and pending/disabled states.

Use one native `src/style.css` with exactly one block for each layer in order: `base, native, components, scaffold, ui, page`. Follow the CSS skill's specificity caps and `:where()` rules, logical properties, role-based tokens, and shared viewport container-query switches. No styling library aside from `@charismaticalli/ui`.

Use indigo/violet accents, pale cool surfaces in light mode, and deep blue-purple surfaces in dark mode. Check text, error, focus, and control contrast in both themes. Match the site's system/light/dark selection behavior, persist under a Budgie-specific storage key, react to OS/cross-tab changes, tolerate unavailable storage, and avoid a wrong-theme flash on startup. Respect reduced motion.

## 7. Verification and completion criteria

Add deterministic Vitest tests for auth initialization/event ordering, subscription disposal, signup without an immediate session, OTP intent/errors, recovery precedence, failed logout, and auth-driven routing. Use injectable SDK boundaries and controlled events rather than real timing sleeps.

Test the query integration against real frappe APIs: no execution with `None`, cached data invalidated on A → B and logout, late A results never displayed to B, and same-user refresh preserving the partition. Test theme resolution and persistence fallback without adding unrelated infrastructure.

Run `pnpm fmt`, `pnpm lint`, `pnpm typecheck`, Budgie tests, relevant frappe tests, and the Budgie production build. Verify runtime dependency count and lockfile consistency.

Deliver a README that lets another developer start local Supabase and Budgie, obtain local email messages, configure GitHub, and run checks. Record the account-persistence follow-up separately. The milestone is complete when real local auth, protected routing, partition lifecycle, and themed placeholder accounts UI all work with these checks passing.
